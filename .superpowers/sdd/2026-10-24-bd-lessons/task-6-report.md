## Implemented

- **One run = one transaction, always rolled back** (`engine/core.js`). A run does BEGIN, SAVEPOINT ora_c, executes, captures the end state if anything changed, and ROLLBACK in a `finally`. Session NLS settings live in JS and are written into the fresh transaction, so they survive the reset while data does not. Runs, `describe` and `snapshot` take turns through a promise queue (overlapping calls cannot interleave transactions).
- **Oracle transaction semantics inside a run.** COMMIT moves `ora_c` forward, ROLLBACK goes back to it, SAVEPOINT / ROLLBACK TO use per-name PG savepoints plus a JS list (so `ROLLBACK TO` an erased or committed savepoint is ORA-01086 instead of aborting the PG transaction). Every statement runs under `ora_s`, so a failed statement undoes only itself (this also fixes the Task 5 cross-check: the `pg_proc` lookup in `failed()` now runs after the rollback to `ora_s`, and a test covers it inside a script). DDL commits implicitly after it ran, also when it fails while running (ORA-00955, ORA-00942 ...), but not when it fails to parse (OracleError from the rewriter or PG 42601). Both facts were measured on Oracle (corpus `ddl:tx.*`).
- **`script: true`** (Ruling R16): `splitScript` (new `engine/script.js`) cuts at `;` and at a line holding only `/`, skipping strings, quoted names and comments; a `DESCRIBE x` line ends at the end of the line. Returns `{ ...last Result, statements: [{ sql, kind, rowCount, error? }] }`, continues after an error. `ALTER SESSION` inside a script goes through the same path (Task 4 cross-check). Without `script: true`, two statements are still ORA-00911.
- **`Engine.describe(table, { dataset })`** and **`Engine.snapshot({ dataset, tables? })`**. After a run that changed something (dml / ddl), both answer for the state that run ended in (captured before the rollback); otherwise for the untouched dataset. A missing table: `describe` gives `[]`, `snapshot` gives a Result with ORA-00942. `DESCRIBE x` / `DESC x` is accepted as a statement (columns Name / Null? / Type, ORA-04043 for a missing table) and works inside a script after a CREATE.
- **Oracle types** (`rewrite/pass-ddl.js`, new, plus `compat/70-ddl.sql`): VARCHAR2/VARCHAR/NVARCHAR2 -> varchar(n), CHAR/NCHAR -> char(n), NUMBER/NUMERIC/DECIMAL(p,s) -> numeric(p,s), DATE -> domain `ora_date` (timestamp(0)), INTEGER/INT/SMALLINT -> `ora_integer`, FLOAT/REAL/DOUBLE PRECISION -> `ora_float`, TIMESTAMP(n), CLOB. Domains exist so DESCRIBE can tell DATE from TIMESTAMP(0) and INTEGER from NUMBER(38). Errors Oracle gives for bad types: ORA-00902, 00906, 00910, 01723, 01727, 01728, 30088. Every PRIMARY KEY / UNIQUE / CHECK / FOREIGN KEY gets a name (the learner's, else a stable `SYS_Cnnnnnn`); duplicate names in one statement are ORA-02264, a doubled NOT NULL is ORA-02258. The CHECK text the learner typed is kept in `ora_check_text` for `user_constraints.search_condition`.
- Also in `pass-ddl.js`: DROP TABLE ... CASCADE CONSTRAINTS / PURGE, `DELETE t WHERE` without FROM, RENAME, ALTER TABLE ADD / MODIFY / DROP COLUMN (DROP COLUMN of the last column is ORA-12983), string literals assigned to DATE columns in INSERT / UPDATE go through the session's date format via `to_date` (so `'2026-02-15'` is ORA-01861 and `'01-JAN-60'` is 1960, as on Oracle), and `INSERT INTO t VALUES` with fewer values than columns is ORA-00947 (PostgreSQL fills the rest). The engine looks up the target table's columns and passes them to `rewriteOracle(sql, { columns })`.
- **`pass-misc.js`**: `DELETE / UPDATE ... WHERE ... ROWNUM <= n` (also `< n`, `= 1`, `> 1`) -> `WHERE ctid IN (SELECT ctid ... LIMIT n)`. (Task 5 listed this as an open concern; it matters now that DML runs.)
- **Dictionary views** in `70-ddl.sql`: `user_tables`, `user_tab_columns` (values measured on the lab tables), `user_constraints` (NOT NULL as type C with `"COL" IS NOT NULL`, delete rule, referenced constraint), `user_cons_columns` (added: needed to see which columns a constraint covers). Compat-layer tables are listed in `ora_internal` and hidden.
- **Errors** (`engine/errors.js`): ORA-00913 / 00947 (arity), 00957, 01430, 01407 (UPDATE to NULL, vs 01400 for INSERT), 01758 / 02296, 02260, 02264 (index name clash), 02266, 02270, 02449, 01086, column name in 00904 for "column of relation", table name in 00942 for DROP, maximum in 12899.
- **`explain.js`**: Romanian + English explanations for 27 new codes (everything above plus 01830, 01839, 01840, 01847, 04043, 12983, 30088).
- **Dataset** (`public/sql/datasets/facultate.sql`): column types are now the ones Oracle reports for the lab tables (`numeric(1,0)`, `numeric(6,2)`, `numeric(2,0)`, `ora_date`), instead of bare `numeric` / `timestamp(0)`. This is what makes `describe('studenti')` equal Oracle's `user_tab_columns`. The 459 earlier queries still match.
- **Oracle harness** (`scripts/sql/oracle.mjs`): the DBMS_SQL procedure is now `AUTHID CURRENT_USER` (as a definer-rights procedure it had no CREATE TABLE privilege through the RESOURCE role: ORA-01031), and a PL/SQL block keeps its final `;`.

Entry format extension: `before` (statements that set the scene, run in the same run / Oracle session), `after` (Oracle-side clean-up only), `beforeErrors` (error codes the scene is expected to raise). `snapshot-oracle.mjs` sweeps `ZT_%` tables before and after, requires the scene to behave as declared, checks the five lab tables are back to 5 tables / 13, 9, 42, 16, 10 rows at the end, normalises `SYS_Cnnnnnn` in error messages and refuses result cells containing one, so two runs give an identical file. `differential.test.js` runs `before` entries as a script and compares the last statement.

## Calls I made (for the decision log; commit says `Decisions: none`)

1. DATE is a domain over timestamp(0) (`ora_date`), INTEGER and FLOAT likewise, so DESCRIBE and `user_tab_columns` are exact; the dataset file now uses them.
2. `describe` / `snapshot` answer for the end state of the last changing run (the run itself is rolled back); a read-only run resets them to the pristine dataset. A missing table is `[]` / an ORA-00942 Result, not a throw.
3. Per-statement savepoints for every statement (cost: two extra round trips per statement) instead of only for scripts.
4. Date strings in INSERT / UPDATE are converted by wrapping the literal in `to_date(...)` after a catalog lookup of the target column types (the rewriter stays synchronous and pure: the engine passes `columns`).
5. A lone `/` line with nothing pending is ignored (SQL*Plus would re-run the previous statement).
6. Corpus scenes: the `before` / `after` / `beforeErrors` format above; DDL tests only touch `zt_` tables, never the lab tables.
7. Granted nothing in Oracle: the privilege problem was in the harness procedure (invoker rights), not in the STUDENT user.

## Concerns

- Approximations that are not in the lab: NCHAR, NVARCHAR2, FLOAT(b), REAL create fine but `user_tab_columns` / DESCRIBE show CHAR, VARCHAR2, FLOAT(126), FLOAT(126). BYTE vs CHAR length semantics are not modelled (VARCHAR2(10) counts characters, Oracle in this container counts bytes, so 10 two-byte letters would pass here and give ORA-12899 there). A TIMESTAMP column is shown like a DATE (`15-FEB-26`), not with time and fraction. CHECK `search_condition` keeps the learner's text only for constraints created through CREATE / ALTER TABLE (always the case in the sandbox); a CTAS table does not copy NOT NULL as Oracle does. No sequences, no `user_objects`.
- `ROWNUM <= n OR ...` in DML is still `ORA-?` (as for SELECT, Task 5 concern).
- `statements[]` entries carry no rows (as Ruling R16 says); the UI for `kind: 'state'` shows the last result and uses `snapshot` for the tables.
- Constraint names in error messages for unnamed constraints are `SYS_Cnnnnnn` from a hash (stable, not Oracle's numbering).
- The Oracle container now needs the harness change (`AUTHID CURRENT_USER`) to run DDL; anyone running `snapshot-oracle.mjs` with the old harness would get ORA-01031.
